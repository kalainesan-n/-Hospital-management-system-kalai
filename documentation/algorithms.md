## 1. Emergency Triage Priority Queue (Min-Heap with FIFO Tie-Breaking)

### 1.1 Problem Statement
In emergency room triage, incoming patients must be seen in order of clinical urgency rather than simple arrival time. However, when multiple patients arrive with the identical severity level, fair clinical protocol requires serving them in strict arrival order (First-In-First-Out).

### 1.2 Data Structure: Binary Min-Heap
We utilize Python's built-in `heapq` module which implements a binary heap satisfying the **Min-Heap Property**:
$$\text{parent} \le \text{children}$$

Each queued entry is stored as a 3-element tuple:
$$\text{Entry} = (\text{priority\_score}, \text{sequence\_counter}, \text{case\_dict})$$

- `priority_score` (Integer $\in \{1, 2, 3, 4\}$):
  - **1 = Critical**: Immediate resuscitation required.
  - **2 = High**: Severe emergency; rapid intervention needed.
  - **3 = Medium**: Urgent; requires clinical evaluation and monitoring.
  - **4 = Low**: Non-acute; standard consultation queue.
- `sequence_counter` (Integer): Monotonically increasing counter generated by `itertools.count()`. In Python, tuples are compared element-by-element from left to right. When two entries share the same `priority_score`, the tuple comparison automatically falls back to `sequence_counter`, guaranteeing strict FIFO ordering without ever comparing dictionary keys.
- `case_dict` (Dictionary): The payload containing patient metadata, symptoms, and vitals.

### 1.3 Time & Space Complexity
| Operation | Time Complexity | Space Complexity | Description |
|---|---|---|---|
| `push(case)` | $\mathcal{O}(\log N)$ | $\mathcal{O}(1)$ | Inserts new emergency patient into the min-heap |
| `pop()` | $\mathcal{O}(\log N)$ | $\mathcal{O}(1)$ | Extracts the highest priority patient from the root |
| `peek()` | $\mathcal{O}(1)$ | $\mathcal{O}(1)$ | Inspects the root item without mutation |
| `sync_from_db()` | $\mathcal{O}(N \log N)$ | $\mathcal{O}(N)$ | Hydrates queue from all pending database records |

## 2. Double-Booking & Conflict Detection Algorithm

### 2.1 Problem Statement
Prevent scheduling collisions where:
1. A doctor is simultaneously booked for two consultations at the same date and time.
2. A patient is booked for consultations with two different doctors at the exact same time.

### 2.2 Algorithm Flowchart / Pseudocode

```python
def check_conflicts(patient_id, doctor_id, date, time, exclude_id=None):
    # Step 1: Doctor conflict check
    doctor_conflict = db.query("""
        SELECT appointment_id FROM appointments
        WHERE doctor_id = :doctor_id
          AND appointment_date = :date
          AND appointment_time = :time
          AND status = 'Scheduled'
          AND appointment_id != :exclude_id
    """)
    if doctor_conflict:
        return (True, "Doctor already has a scheduled appointment at this time.")

    # Step 2: Patient conflict check
    patient_conflict = db.query("""
        SELECT appointment_id FROM appointments
        WHERE patient_id = :patient_id
          AND appointment_date = :date
          AND appointment_time = :time
          AND status = 'Scheduled'
          AND appointment_id != :exclude_id
    """)
    if patient_conflict:
        return (True, "Patient already has another appointment booked at this time.")

    # Step 3: Doctor roster status check
    doctor = db.query("SELECT status FROM doctors WHERE doctor_id = :doctor_id")
    if doctor.status != 'Active':
        return (True, f"Doctor is currently {doctor.status}.")

    return (False, "No conflict detected.")
```

### 2.3 Time Complexity
Thanks to compound indexing on `(doctor_id, appointment_date, appointment_time)` and `(patient_id, appointment_date, appointment_time)`, MySQL executes these lookups in $\mathcal{O}(\log M)$ B-Tree index traversal time, where $M$ is the number of appointment rows.

## 3. Transactional Bed Allocation & Atomic Release

### 3.1 Problem Statement
Hospital beds must never be double-allocated. When a patient is discharged, the bed must immediately and reliably become available for other admissions.

### 3.2 Concurrency Control with Pessimistic Row Locking (`FOR UPDATE`)
To avoid race conditions:
```sql
-- Admission Transaction:
START TRANSACTION;
SELECT status FROM beds WHERE bed_id = :bed_id FOR UPDATE;
-- Verify status == 'Available'; if not, ROLLBACK;
INSERT INTO admissions (patient_id, bed_id, status) VALUES (...);
UPDATE beds SET status = 'Occupied' WHERE bed_id = :bed_id;
COMMIT;
```

```sql
-- Discharge Transaction:
START TRANSACTION;
SELECT bed_id FROM admissions WHERE admission_id = :adm_id FOR UPDATE;
UPDATE admissions SET status = 'Discharged', discharge_date = NOW() WHERE admission_id = :adm_id;
UPDATE beds SET status = 'Available' WHERE bed_id = :bed_id;
COMMIT;
```

## 4. Key Stretching & Cryptographic Password Hashing (PBKDF2-HMAC-SHA256)

### 4.1 Algorithm Description
Simple SHA-256 or MD5 hashes are vulnerable to rainbow table lookups and brute-force GPU crackers.
To prevent this, we utilize **PBKDF2 (Password-Based Key Derivation Function 2)** with HMAC-SHA256:

$$\text{DerivedKey} = \text{PBKDF2}(\text{HMAC-SHA256}, \text{Password}, \text{Salt}, c = 100000, \text{dkLen} = 32)$$

- **Salt**: 16 bytes (32 hex characters) generated via OS entropy pool (`secrets.token_hex(16)`).
- **Key Stretching**: 100,000 iterations dramatically increases the computational cost of brute-force attacks.
- **Constant-Time Verification**: Verification uses `secrets.compare_digest()` to eliminate timing attack vulnerabilities.
