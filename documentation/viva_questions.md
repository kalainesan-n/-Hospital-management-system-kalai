# College Viva Voce Examination & Technical Defense Guide

This document contains expected questions from external examiners, university professors, and project evaluators, paired with articulate, senior-level technical answers.

---

### Q1: What is the core problem your project solves?
**Answer**:
Modern hospitals face operational bottlenecks in three main areas:
1. Fragmented patient tracking across outpatient consultations and inpatient admissions.
2. Inefficient bed utilization leading to overbooking or underutilization.
3. Lack of triage prioritization in emergency intake.

Our system provides an integrated desktop platform built in Python with MySQL that automates outpatient scheduling with conflict detection, manages inpatient bed life-cycles transactionally, implements an algorithmic priority queue for emergency triage, and derives real-time visual analytics using Pandas and Matplotlib.

---

### Q2: Why did you choose Tkinter instead of a Web Framework (Django, Flask, React)?
**Answer**:
1. **Desktop Native Performance**: In clinical settings, workstations in nursing stations, triage desks, and administrative counters benefit from responsive, low-latency native desktop software that runs directly on local hardware without depending on external web server hosts or network latency.
2. **Offline-Capable Local Architecture**: Hospital intranets are often air-gapped or restricted for privacy and HIPAA/data security reasons.
3. **Embedded Visuals**: Tkinter integrates directly with Matplotlib via `FigureCanvasTkAgg`, rendering dynamic chart canvases natively without browser overhead or JavaScript dependencies.

### Q3: Explain how your Emergency Triage Priority Queue works mathematically and programmatically.
**Answer**:
We implemented an educational triage simulation using Python's standard `heapq` library, which enforces the **Binary Min-Heap Property** ($\mathcal{O}(\log N)$ insertion and deletion):
1. **Priority Scale**:
   - Critical = Score 1
   - High = Score 2
   - Medium = Score 3
   - Low = Score 4
2. **Tuple Heap Structure**:
   `entry = (priority_score, sequence_counter, case_data)`
3. **FIFO Tie-Breaking**:
   If two patients arrive with identical severity (e.g., both are `Critical`), Python compares the next tuple element: `sequence_counter` (generated by `itertools.count()`). This mathematically guarantees strict arrival order without ever comparing arbitrary dictionary keys.
4. **Academic Disclaimer**:
   The module explicitly includes an academic banner noting that this is an educational algorithmic demonstration of priority queues, not clinically validated triage.

### Q4: How do you prevent double-booking for appointments?
**Answer**:
When an appointment is scheduled or rescheduled, our `AppointmentService` performs two atomic queries:
1. **Doctor Schedule Check**:
   Queries `appointments` for any `Scheduled` appointment where `doctor_id = :d`, `appointment_date = :date`, and `appointment_time = :time`.
2. **Patient Schedule Check**:
   Queries `appointments` for any `Scheduled` appointment where `patient_id = :p`, `appointment_date = :date`, and `appointment_time = :time`.

If either query returns a record, the transaction is rejected with a descriptive conflict notification. Compound indexes on `(doctor_id, appointment_date, appointment_time)` and `(patient_id, appointment_date, appointment_time)` ensure this query executes in sub-millisecond $\mathcal{O}(\log M)$ B-Tree lookup time.

### Q5: How do you handle bed allocation and discharge integrity?
**Answer**:
Bed allocation is tied directly to inpatient admissions within an ACID transaction:
1. **Admission**:
   - Evaluates if the bed's status is `Available`.
   - Inserts the `admissions` row and updates `beds.status = 'Occupied'` within the same transaction. If an error occurs, the entire operation rolls back.
2. **Discharge**:
   - Updates `admissions.status = 'Discharged'` and sets `discharge_date` and `total_amount`.
   - Automatically executes `UPDATE beds SET status = 'Available' WHERE bed_id = :b`, releasing the bed immediately.
   - Historical records are completely preserved.

### Q6: How is user authentication secured in the database?
**Answer**:
Passwords are never stored in plaintext. We implement **PBKDF2-HMAC-SHA256**:
1. A unique 32-character hexadecimal salt is generated using `secrets.token_hex(16)`.
2. The password is key-stretched with 100,000 iterations of HMAC-SHA256.
3. During login, the password is re-hashed using the stored salt and verified using `secrets.compare_digest()` to eliminate timing attack vectors.

### Q7: How are Pandas and Matplotlib utilized in the Analytics module?
**Answer**:
1. **Pandas**: Queries live records from MySQL and transforms them into DataFrames. We compute aggregations such as:
   - Daily patient registration frequency.
   - Doctor workload distribution (Total vs. Completed).
   - Ward capacity breakdown (Occupied vs. Available).
   - Emergency severity distributions and average patient ages.
2. **Matplotlib**: Renders these DataFrames into 6 specialized charts (bar charts, line trends, pie/donut charts) using the application's slate dark palette, and embeds them directly inside Tkinter via `FigureCanvasTkAgg`.

### Q8: What database constraints ensure referential integrity?
**Answer**:
1. Foreign keys with `ON DELETE RESTRICT` on core clinical entities (patients, doctors, beds) prevent accidental orphaned records.
2. `ON DELETE SET NULL` on `emergency_cases.assigned_doctor_id` ensures emergency logs are preserved even if an emergency physician record is deactivated.
3. Unique constraints on `patient_code`, `doctor_code`, `appointment_code`, `bed_number`, `admission_code`, and `case_code` prevent duplicate business codes.
